# 账号权限管理

## 给同事开通权限

1. 同事先注册账号，或从门户进入租赁系统完成首次登录。
2. 使用现有「老板」账号登录，进入「花名册 · 提成」的「花名册 · 账号权限」。
3. 点击「刷新账号与权限」，核对成员的**登录账号和登录方式**。同名人员可能有不同账号，按实际登录的账号操作。
4. 点击「改权限」，选择所需角色，保持「账号启用」，保存。
5. 同事回到系统窗口、切换页面或刷新，界面会同步角色；服务端在下一次请求就执行新权限，无需重新签发登录令牌。

日常授权由应用里的老板完成，不需要把服务器 SSH 密钥交给同事。「老板」同时具有系统管理和业务审批权限，仅授予确实需要这些权限的人。普通成员需要业务操作权限时，按职责选择供应链、财务或业务等角色。

## 页面规则

- 列表直接读取真实登录账号，包含本地注册、门户登录及停用的账号；首次登录后无需另建花名册条目。
- 成本等敏感字段和客户行级限制由角色决定，页面显示服务端 `DataScope` 的实际规则。旧的自定义权限文字和开关未接入鉴权，现已移除，避免出现保存成功却不生效的情况。
- 停用账号会阻止其后续访问；重新启用后，未过期的原会话仍可使用。停用不是永久注销令牌。
- 系统至少保留一个启用的老板，禁止停用或降级最后一个老板；多个管理员并发操作也会重新验证权限。
- 修改及越权尝试记录到审计日志。账号修改的审计对象类型是 `auth_user`，对象主键是登录账号 ID。
- 如果弹出“权限管理已切换到登录账号”，刷新浏览器后再操作，不能把旧花名册主键当作账号 ID。

## 部署与已有数据

本次改动需要部署后端和前端，**无需新增数据库表、字段或手动 SQL 迁移**。后端应先部署；尚未更新的旧前端保存权限时会收到刷新提示，不会误改账号。

历史 `yc_rent_user_role_ext` 的姓名、角色、提成归属可能与登录账号不同。本次不按姓名猜测合并，不改变客户、任务、投资人、历史提成的归属，也不把历史角色批量覆盖到登录账号。已有权限以账号表为准，管理员可在新页面逐个核对授权。

如果当前系统已没有任何启用的老板账号，由负责人按下面的一次性恢复步骤创建新管理员。恢复后，日常授权使用页面完成。

## 没有可用老板账号时：一次性恢复

先部署包含本次修复的后端和前端，再由有部署权限的负责人打开服务器或部署平台的终端，在仓库目录运行：

```bash
bash deploy/recover-admin.sh test
```

1. 在隐藏输入提示中输入临时密码。按本次需求可输入 `123456`；它不能单独取得系统权限。
2. 命令只新建一个 `test` 待激活管理员，并显示随机的一次性恢复码，**30 分钟内有效**。恢复码不写入仓库，数据库只保存哈希。
3. 打开系统登录页，输入 `test` 和临时密码，进入「激活恢复管理员」。
4. 输入控制台显示的恢复码，设置至少 12 位、包含字母和数字的新密码。激活后立即进入花名册；临时密码和恢复码同时失效。
5. 给自己的日常账号分配老板角色，再给同事分配对应业务角色。需要时可用日常老板账号停用恢复账号。

命令复用运行中的 `worland-server` 容器数据库环境，密码只经标准输入传递，不要求同事持有 SSH 密钥。建号不会自动随服务启动执行，也没有匿名建管理员接口。`status=2` 表示恢复待激活，无业务访问权限；激活后变为 `status=1`，不新增数据库字段。

如果 `test` 已存在，命令会拒绝，**不会覆盖密码、启用或提升已有同名账号**。改用一个新名称，例如 `bash deploy/recover-admin.sh test_recovery`。恢复码过期或丢失也应创建新的恢复账号，恢复成功后在花名册停用不用的待激活账号。

GitHub 的 `main` 更新只代表代码已发布；只有部署新版本、执行命令并完成激活后，线上账号才真正存在且可用。恢复码只交给需要恢复权限的负责人，勿放在公开工单或仓库里。
