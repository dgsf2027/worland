# 合同付款方式 + 维保并入资产管理 + 转让关联台账 + 财务测试数据清理

日期：2026-09-28 · 状态：待评审

## 背景与目标

四项改动，来自使用中发现的问题：

1. **采购入库·应付**：付款条件现在挂在设备上（`yc_rent_asset_payment_term`），一份合同下的设备各自一套，容易不一致；而且应付只在触发点生成——尾款要等入库才存在，所以**累计应付看不到未触发阶段**，负债被低估。改为以合同付款方式为唯一真相源，并与租赁台账打通；任一付款条件挂上即计入累计应付与未付。
2. **维保工单**：独立模块，和资产管理并列，但两边都在管"东西坏了怎么修"。并入资产管理，且仓库物品也要能报修。
3. **转让·处置**：页面要手填数字 ID（"设备ID""合同ID"），与租赁台账没有可点的关联。双向打通。
4. **财务三模块**（凭证中心、现金流/分配驾驶舱、月度报表）残留测试期数据，来源单据早已删除。按"来源单据是否还在"清理。

不在范围内：收租侧逻辑、供应商模块、审批流。

## 一、合同付款方式（关联租赁台账）

### 口径

**合同是付款方式的唯一真相源。** 一份设备租赁合同定义一套多段付款方式；该合同下的台账设备与采购单全部继承，不再逐台维护。

**任一付款条件一旦挂上，就计入累计应付与未付**——不再等"下单/入库"触发。

### 数据模型

新表 `yc_rent_contract_payment_term`：

| 列 | 说明 |
|---|---|
| `contract_id` | 合同 |
| `seq` | 段序号 |
| `stage_name` | 阶段名（首付/验收/尾款…，16 字内，同合同内不重复，「退款红字」保留） |
| `ratio` | 比例 0-1，同合同各段合计 = 100% |
| `trigger_point` | 下单 / 入库 |
| `due_days` | 触发日 + N 天 |

校验规则沿用现有 `AssetPaymentService.normalize`（原样搬到合同层，行为不变）。

`yc_rent_asset_payment_term` **停止写入**，保留读取，只为映射不到合同段的历史应付服务。设备的预计付款金额改为**算出来不存**：该设备合同价 × 合同段比例，前 N-1 段四舍五入到分、末段补差（沿用 `expectedAmounts`）。

`yc_rent_payable.term_id` 改指向 `yc_rent_contract_payment_term.id`。

### 应付生成时点

采购下单时**一次生成全部阶段**的应付，而不是分两次：

- `trigger_point=下单` 的段：到期日 = 下单日 + `due_days`
- `trigger_point=入库` 的段：入库前用**预计入库日** + `due_days`，并打上"到期日为预估"标记；实际入库时改写为真实入库日 + `due_days` 并清除标记

为此：
- `yc_rent_purchase_in` 新增 `expect_receive_date`（预计入库日，默认 = 下单日 + `rule_config[purchase_lead_days]`，新增该规则项，默认 30 天，可在下单时改）
- `yc_rent_payable` 新增 `due_provisional tinyint(1)`（1 = 到期日按预计入库日推算）

这样每笔应付都有到期日，现金流驾驶舱的到期分层与兑付缺口 T-N 扫描不需要改口径；界面上"预计"的到期日标注出来，不与已确定的混淆。

### 与租赁台账的关联

- **台账 → 合同**：设备详情的付款计划显示"继承自合同 {合同号} 的付款方式"，逐段列出阶段名/比例/触发点/账期/预计付款金额/对应应付（金额、到期日、是否预估、状态），以及该设备的累计应付、已付、未付合计。设备上不再能单独编辑付款条件，改为一个跳转到合同的链接。
- **合同 → 台账**：合同的付款方式区块下方列出它覆盖的台账设备（品类·型号·序列号·合同价）与各段的合计预计付款金额，即"这套付款方式一共要付多少钱、分几笔"。
- 台账列表增加「未付」列（成本口径，对 GP/LP 打码）。

### 已付阶段的保护

已有"已付"应付的阶段：比例不能改、段不能删（现有 `updateTerms` 的保护逻辑上移到合同层）。合同付款方式修改时，只重算"待付"应付，已付的锁定不动。

### 采购下单的变化

下单弹窗不再让人填付款条件，改为只读显示继承来的合同付款方式 + 一个"到合同里修改"的链接。若合同还没设付款方式，下单时按 `rule_config[payable_stage_ratio]` 默认三段写入该合同并提示。

### 数据迁移（V118）

1. 建表。
2. 每份未删合同的付款方式，从它名下设备现有的 `asset_payment_term` 反推：
   - 全部设备条件一致 → 直接用那一套
   - 不一致 → 取覆盖设备最多的那套，并在合同备注里追加一行说明（列出被丢弃的差异），便于人工复核
   - 名下一台设备都没有条件 → 用 `rule_config[payable_stage_ratio]` 默认三段
3. `payable.term_id` 按**阶段名**映射到新的合同段 id；映射不上的保留原值，并在 `remark` 追加"(历史条件)"。
4. 为已有采购单补齐未触发阶段的应付：状态非"已红冲"、设备有合同价、该阶段尚无应付行的，插入"待付"应付，到期日按预计入库日（`expect_receive_date` 回填 = `order_date` + 30 天）推算并标 `due_provisional=1`，备注"合同付款方式补齐"。
5. `purchase_in.expect_receive_date` 回填：已入库的用 `receive_date`，未入库的用 `order_date + 30`。

**这一步会让生产库的累计应付与未付变大**——这是预期效果（原先被低估），但财务对账会看到跳变，所以补出来的行统一带"合同付款方式补齐"备注便于识别。

## 二、维保工单并入资产管理

### 数据模型

`yc_rent_maintenance` 增加：

| 列 | 说明 |
|---|---|
| `target_type` | `asset` / `inv_item`，NOT NULL DEFAULT 'asset' |
| `inv_item_id` | 仓库物品，可空 |
| `qty` | 送修数量，仅 `inv_item` 用，默认 1 |
| `movement_out_id` / `movement_back_id` | 关联的出入库流转记录 |

`asset_id` 改为可空。服务层保证：`target_type=asset` → `asset_id` 必填且 `inv_item_id` 为空；`target_type=inv_item` → 反之。`bom_id`（故障配件）只在 `target_type=asset` 时可用。

### 仓库物品报修走已有的数量流转

`repair_qty` 的唯一写手仍是资产管理的出入库流转（`InvService`），维保工单只是它的单据封装：

- **建单（报修）**：调「送修」把 `qty` 件从库存移到维修中，把 movement id 记在工单上
- **完工**：按处理结果调「修好」（维修中→库存）或「报废」（维修中→已报废），记第二个 movement id
- **关闭（未修）**：调「修好」退回库存，备注未处理

不另记一套库存状态，避免双账。

### 页面

- 资产管理模块（`/inventory`）新增「维保工单」标签页：列表 + 报修/派工/回写，原样搬过来。
- 报修时先选对象类型（台账设备 / 仓库物品），再从对应列表里搜索选择——不再手填 ID。选仓库物品时多一个数量输入。
- 左侧「🔧 维保工单 · 报修/回写」菜单项撤掉；`/maintenance` 路由保留并重定向到 `/inventory`，旧书签不至于 404。
- 质保内/责任方/费用/配件故障计数的逻辑不变。

## 三、转让·处置关联资产台账

### 台账 → 转让

三个页签里的手填 ID 全部改成搜索选择器：

- **到期转让**：合同选择器（合同号 · 客户 · 状态 · 剩余期数），选中后列出该合同挂载的设备供确认
- **复投飞轮（处置）**：设备选择器（品类 · 型号 · 序列号 · 状态 · 账面价），二手处置时账面价直接显示出来，方便判断是否触发名义价守卫
- **列表/详情**：显示设备标签而不是裸 id，可点击跳转台账

后端 `TransferDtos` 的列表行与详情行补：`assetLabel`、`serialNo`、`category`、`model`、`assetStatus`、`bookValue`、`contractNo`、`customerName`。

### 转让 → 台账

- 设备详情新增「转让/处置记录」区块：单号、类型（转让/收回/二手/报废）、处置价、处置损益、状态、业务时间，可点进转让单。
- 台账列表新增「处置状态」列：无记录显示 `—`，有则显示最近一次的类型与状态，支持按它筛选。

## 四、财务测试数据清理（V117）

按"来源单据是否还在"界定：

| 对象 | 处理 |
|---|---|
| 凭证 `yc_rent_voucher` | 来源单据已逻辑删除或查不到的 → 逻辑删 + 凭证号加 `#DEL{id}`。来源类型与 id 对应关系：`rent_bill`→收租单、`purchase_in`→采购单、`transfer_line`→转让行、`depreciation`→设备。`manual` 手工凭证保留（无来源单据可判） |
| 凭证分录 `yc_rent_voucher_line` | 随凭证逻辑删 |
| 总账流水 `yc_rent_ledger_book` | 随凭证**物理删**（该表无 `is_deleted` 列） |
| 折旧行 `yc_rent_asset_depreciation_line` | 设备已删或查不到的 → 逻辑删 |
| 结账分配 `yc_rent_rent_distribution` | 全部清空 —— 按期间汇总、没有合同维度，现存的都是测试期跑的（该模块只有这一张表，无明细表） |
| 月度报表 `yc_rent_monthly_report` | 全部清空，同上 |
| 出资人名册 `yc_rent_investor` | **保留** —— 数智云仓/小洪/刘总/其他出资方是真实出资结构 |
| LLM 调用日志 `yc_rent_llm_call_log` | **保留** —— 接口调用审计，不是业务数据 |

500 万红线是从 `ledger_book` 现算的，没有独立数据，跟着上面一起干净。

## 迁移拆分与实施顺序

三条迁移分开，出问题好定位：

- **V117**：财务测试数据清理（第四项，与其他三项无依赖）
- **V118**：合同付款方式建表 + 数据迁移 + 应付补齐（第一项）
- **V119**：维保工单加对象类型维度（第二项）

第三项纯代码，不动表结构。

四项相互独立，按风险从低到高实施，每项独立提交，随时可以停：

1. **第四项**（V117 清理）—— 最简单，先做完验证链路
2. **第三项**（转让关联台账）—— 纯前后端 DTO 与选择器，无表结构
3. **第二项**（维保并入资产管理，V119）
4. **第一项**（合同付款方式，V118）—— 改动面最大，放最后，前面几项已经把验证流程跑热

`yc_rent_reminder`（提醒）不在本次范围内，那是按当前数据现算的派生提醒，清完上游自然干净。

## 风险

1. **累计应付与未付的数字会变大**（V118 补齐未触发阶段）。这是修正低估，但财务看到跳变会疑惑；补出来的行带统一备注，且在采购单详情里"预计"到期日有标注。
2. **合同付款方式反推可能不唯一**。不一致时取覆盖设备最多的那套并在合同备注留痕，需要人工复核——迁移后我会给出一份需复核的合同清单（只能在有服务器权限的人那边跑 SELECT，我看不到生产数据）。
3. **`payable.term_id` 映射按阶段名**。改过阶段名的历史数据映射不上，保留原值并标"(历史条件)"，不影响金额与到期日。
4. **维保菜单撤掉**后，习惯从左侧进入的人要改从资产管理进；路由重定向兜住旧书签。
5. 生产部署仍需有服务器权限的人执行，我没有权限。
